# 설계와 수행 범위

## 목적

개인 알고리즘 학습에 쓸 로컬 모델을 선택하기 위해, 설명의 인상과 생성 코드의 실행 결과를 함께 비교했습니다. 로컬 서버의 실행 조건을 직접 다루고 외부 API 모델을 같은 공개 문제에 적용하는 것이 중심이었습니다.

COCI 문제를 사용한 이유는 문제문뿐 아니라 공식 테스트 데이터를 확보해 로컬에서 반복 채점할 수 있기 때문입니다. 모델 입력에는 문제 설명과 공식 제한을 제공하고, 정답 코드·풀이·비공개 채점 입력은 넣지 않았습니다. [요구사항](requirements.md)과 [평가 질문](evaluation-questions.md)에 범위가 있습니다.

## 직접 수행한 범위와 구현 지원

- **직접 수행:** 로컬 LLM 서버 구동, GPU 레이어 수를 포함한 추론·서빙 옵션 조정, 외부 API 호출을 통한 공개 코딩 문제 비교
- **도구 구현·유지보수:** Python CLI 통합, API 어댑터 확장, 저장·재개·잠금·Judge·평가 기반 작업에 AI 지원을 활용
- **결과 설명:** 저장된 요청 조건·응답·판정과 개인 사용 목적을 연결해 비교합니다. 코드의 존재와 실험 수행, 구현 지원 범위를 구분합니다

구현·모의 검증의 담당과 시점은 [유지보수 이력](../history/maintenance-log.md)에 남아 있습니다. 개인 프로젝트라는 말은 팀 프로젝트가 아니라는 뜻이며, 모든 코드를 AI 도움 없이 작성했다는 뜻으로 쓰지 않습니다.

## 추론과 서빙 파라미터 탐색

서버 실행 셸에 남긴 옵션뿐 아니라 당시 노출된 다른 옵션도 바꿔 보며 동작과 성능을 살폈습니다. 이 과정은 모델 가중치를 학습하는 파인튜닝이 아니라 **추론·서빙 설정 탐색**입니다.

현재 저장된 셸의 주요 값은 다음과 같습니다.

| 설정 | Qwen3.6 | Gemma4 |
| --- | --- | --- |
| GPU 레이어 | `--gpu-layers all` | `--gpu-layers auto` |
| CPU MoE 배치 | `--n-cpu-moe 32` | 셸에 지정하지 않음 |
| 적재 방식 | `--load-mode none` | `--load-mode auto --lazy-mode auto` |
| 메모리 적합 설정 | 셸에 지정하지 않음 | `--fit on --fit-target 0` |
| 생성·배치 스레드 | `--threads 16 --threads-batch 24` | 같음 |
| context·출력·reasoning 예산 | 65,536 · 61,440 · 53,248 | 같음 |
| 공통 설정 | `--parallel 1 --flash-attn on --temp 0 --reasoning on --cache-ram 0` | 같음 |

원본은 [Qwen 셸](../../configs/llama.cpp/qwen36.sh)과 [Gemma 셸](../../configs/llama.cpp/gemma4.sh)입니다. 지정하지 않은 옵션을 꺼진 기능으로 해석하지 않으며, 실제 기본 동작은 해당 런타임 버전에 달려 있습니다.

이 표는 최종 저장 설정입니다. 모든 탐색 조합·시점·대조 측정이 보존된 것은 아닙니다. 또한 현재 셸은 과거 실행 이후 바뀐 부분이 있어, 개별 실행의 조건은 해당 `result.json`과 당시 로그를 먼저 봐야 합니다. 이전 context 조건의 진단값을 최종 benchmark 결과와 합치지 않습니다. [환경 관측과 설정 이력](../operations/environment.md)이 그 경계를 설명합니다.

## 시행착오에서 확인한 것

추론 속도가 떨어졌을 때 스레드 수별로 진단하고 생성용·배치용 스레드와 CPU·GPU 배치를 나누어 조정했습니다. 당시의 단일 decode 진단과 서버 실행 관측은 최종 64K benchmark와 조건이 달라, 같은 성능 개선 수치로 합치지 않습니다.

출력 전환도 정답성과 구분했습니다. reasoning 종료 메시지를 추가한 Qwen 진단에서는 최종 설명과 코드가 생성됐지만 원본 판정은 RE였습니다. 코드가 나오게 된 것을 정답률 개선으로 계산하지 않고 진단 기록으로 남겼습니다. [당시 진단과 증빙 범위](../history/reasoning-budget-diagnostic.md)를 참고하세요.

## 문제를 나누어 확인한 방법

### 생성 품질과 실행 성능

답변을 받는 것과 정답 코드를 얻는 것을 구분했습니다. 응답은 있어도 코드가 추출되지 않으면 `NO_CODE`로 남기고, 코드가 있어도 실행 결과에 따라 `AC`, `WA`, `RE`, `TLE` 등을 기록합니다. 설명의 타당성은 별도 기준으로 검토합니다.

### 모델 실행과 채점의 자원 경합

로컬 모델 서버가 실행 중이면 채점 프로세스와 자원을 다툴 수 있습니다. 생성 단계와 채점 단계를 분리하고, 생성·채점 경로에 잠금과 프로세스 확인을 두었습니다. 이 구현은 [작업 경계](../../src/llm_eval/shared/workloads.py)에서 볼 수 있습니다.

### 원본 결과와 보조 실험

원본 응답·코드는 보존하고 시간 제한을 완화한 재평가와 최소 수정본 채점을 별도로 남겼습니다. 호출 실패도 시도 수에서 빼지 않았습니다. [평가 절차](../operations/evaluation.md)와 [보고서](model-selection-report.md)에서 공식 제한과 프로젝트 정책 결과를 함께 확인할 수 있습니다.

### 기록을 읽을 때의 주의

요청 전체 경과 시간, llama.cpp가 보고한 생성 속도, 장치 전체 GPU 사용량, 클라우드 토큰·비용 추정은 서로 다른 지표입니다. 값이 없으면 0으로 채우지 않고 사유와 함께 `null`을 남깁니다. [기록 점검](../operations/recording.md)에 수집 범위가 있습니다.

## 결과와 다음 검증

최종 기록은 10문항 × 4모델 × 2회 요청으로, 80회 시도 중 정상 응답 78건과 호출 실패 2건을 포함합니다. 공식 1배 시간 제한 AC와 일부 문항의 2배 제한을 반영한 프로젝트 지표는 분리합니다. 원본 코드 수정 후의 통과는 원본 정답률에 더하지 않습니다.

작은 공개 문제 집합이므로 학습 데이터에 문제나 풀이가 포함됐는지 확인하지 못했고, 다른 과제에 대한 일반화 성능도 입증하지 않았습니다. 후속 검증 후보는 데이터셋 확대·오염 가능성 점검, 사전 확정한 평가 정책, 실행별 설정·모델 해시 고정과 파라미터 대조 측정입니다.

이 문서는 기존 실험의 목적·기여·해석 경계를 설명합니다. 새로운 튜닝 성과나 실험 완료를 추가한 기록은 아닙니다.
