# 평가 질문 10개와 기대 결과

[프로젝트 범위](assignment.md)에 맞춰 질문별 ID·입력 자료·기대 결과와 사례 구분을 기록한다.

## 작성 시점을 먼저 밝힌다

**이 문서는 생성과 채점이 끝난 뒤 작성했다.** 문항 10개 선정과 공통 프롬프트·생성 설정은 본 실험 전에 확정했지만, 질문별 기대 결과를 이 형식으로 문서화한 것은 사후다. [요구사항](requirements.md)의 `decision_phase=during_generation`·`preregistered=false`와 같은 맥락이며, 사전등록된 기준으로 표시하지 않는다. 문항·프롬프트·제한값은 이 문서를 쓰면서 바꾸지 않았다.

## 공통 조건

네 모델에 같은 문제문과 같은 지시문을 보낸다. 프롬프트는 [problems.py](../../src/llm_eval/shared/problems.py)의 `build_problem_prompt`가 만들며, 문제문 바로 위에 공식 시간·메모리 제한을 넣는다. 다른 메타데이터(난이도, 대회 정보, 배점)는 전달하지 않는다.

요구하는 출력은 네 가지다.

1. 문제 해결 접근법 설명
2. 시간 복잡도와 공간 복잡도 설명
3. stdin에서 읽고 stdout으로 쓰는 실행 가능한 Python 3 정답 코드
4. 최종 답변에 실행 가능한 코드 블록을 **정확히 하나만** 포함

제공자별 생성 설정은 다르다. 로컬 두 모델은 `temperature=0`·`max_tokens=61440`·`reasoning_budget_tokens=53248`, Luna는 Responses API에 `reasoning=max`·`max_output_tokens=128000`, Motif-3는 모델과 단일 user 메시지만 보내고 나머지는 제공자 기본값이다. 문제 목록·반복 수·독립성만 공통 조건으로 삼는다.

## 기대 결과의 판정 방식

이 태스크의 기대 결과는 서술형 모범답안이 아니라 **공식 테스트 데이터 전량 통과**다. 각 문항의 정답은 COCI가 공개한 입출력 쌍으로 확정돼 있어 채점자의 해석이 들어가지 않는다. 그래서 질문별 "기대 결과" 칸에는 그 문항에서 반드시 도달해야 하는 핵심 관찰과 통과 기준을 적는다.

설명 품질은 별도 축이다. 접근법·정당성·복잡도를 2/1/0으로 채점하며 기준은 [요구사항](requirements.md#설명-정확성)에 있다.

## 사례 구분

발제는 정상·경계·정보 부족/범위 밖 사례를 포함하라고 요구한다. 이 태스크에 그대로 대응되는 것과 대응되지 않는 것을 구분해 적는다.

### 정상 사례

표준적인 알고리즘 문제 풀이에 해당한다. 난이도 1~5의 6문항(`skare`, `cokolada`, `dzeparac`, `tomahawk`, `struktura`, `tezina`)이 여기 속한다. 접근법이 한두 개의 관찰로 정리되고 구현 분량도 크지 않다.

### 경계 사례

두 층위가 있다.

**문제 제약의 경계.** 입력 크기가 순진한 풀이를 배제하도록 설계된 문항이다. `dzeparac`는 N이 10^18까지, `struktura`는 n이 10^9까지, `tomahawk`는 n이 10^9까지다. 전체를 만들거나 순회하면 반드시 실패하므로, 모델이 제약을 읽고 접근을 바꾸는지가 드러난다.

**테스트 데이터 안의 경계.** 각 문항의 공식 테스트 41~130개에는 최소 입력과 상한 입력이 포함돼 있다. 이 부분은 COCI가 설계한 것이고 내가 만든 것이 아니다. 실제로 `prepisivanje`에서 Gemma가 130개 중 120개를 통과하고 남은 10개에서 `RecursionError`로 무너진 것이 이 층위의 경계가 작동한 사례다.

**난이도 상한.** `skijanje`(난이도 9)는 두 로컬 모델이 모두 출력 한도를 소진해 코드를 내지 못했다. 후보의 능력 상한을 재는 의도적 배치다.

### 정보 부족·범위 밖 사례 — 두지 않았다

**이 태스크에는 두지 않았고, 억지로 만들지도 않았다.** 이유를 밝힌다.

발제의 이 항목은 고객 상담·문서 질의응답처럼 **답할 수 없는 질문을 모델이 거절할 수 있는지** 보려는 것이다. 그런데 COCI 문제문은 입력 형식·제약·출력 형식이 모두 명시된 완결된 명세이고, 정답은 공식 테스트 데이터로 확정돼 있다. 정보가 부족한 문제문을 만들려면 공식 문제문을 훼손해야 하는데, 그러면 공식 테스트 데이터로 채점할 수 없게 되어 이 저장소의 판정 방식 자체가 무너진다.

대신 [요구사항](requirements.md)에서 **그림이 있어야 풀 수 있는 문제를 후보에서 제외**했다. 텍스트만으로 해결 가능한 문제로 범위를 한정한다는 규칙이고, 이것이 "범위 밖"에 대한 이 프로젝트의 대응이다. 제외 판단은 문항 선정 시점에 했다.

한계로 남긴다. **"모를 때 모른다고 답하는가"는 이번 평가에서 측정하지 않았다.** 대신 관측된 것은 다른 실패 양상이다. 모델은 풀 수 없는 문항에서 거절하지 않고 추론을 계속하다 출력 한도를 소진했고(`skijanje` 4건), 한 경우에는 "완전한 구현을 제공하겠다"는 주석만 남긴 채 코드를 비웠다(`ucionica` Gemma 2건). 상세는 [생성 기록 진단](../history/generation-diagnostics.md)에 있다.

## Cloud 문항 선정

발제 STEP 7은 Cloud 1개에 사전 선정한 공통 5문항을 1회씩 적용하도록 한다. 이번 수행은 [확장 기준](requirements.md#cloud-비교-확장-기준)에 따라 Luna·Motif-3 두 제공자에 **같은 10문항을 2회씩** 적용했다. 별도의 5문항 부분집합을 만들지 않았으므로 "결과를 보기 전에 5문항을 골랐다"는 요건은 해당되지 않으며, 대신 전체 문항을 그대로 쓴 것으로 대체했다. 이 확장은 일부 로컬 결과를 본 뒤 결정했고 사전 선정으로 소급하지 않는다.
