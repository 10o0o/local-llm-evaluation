## 사용 사례

개인 알고리즘 학습용으로, 문제 설명에서 접근법·정당성·시간/공간 복잡도 설명과 실행 가능한 Python 정답 코드를 얻는다. 정답 코드를 우선한다. 그림 없이 텍스트만으로 해결 가능한 문제로 범위를 한정하며 그림을 봐야 풀 수 있는 문제는 제외한다.

아래는 발제 공통 기준과 구분한 사용자 정의 기준이다. License는 개인 이용 조건과 준수사항을 확인하며 상업적 이용 가능 여부는 필수 통과 조건으로 두지 않는다. 현재 장비에서의 실행 가능성·입출력 길이 수용·License 조건의 실제 충족 여부는 별도로 확인한다.

## 난이도 범위

문제 난이도는 본인의 체감을 기준으로 1~10으로 구분한다. 외부 사이트의 공식 난이도를 환산한 척도는 아니며, 다음 세 수준을 기준점으로 삼는다.

- **1:** AtCoder ABC 초반~중반 문제 수준
- **5:** AtCoder ABC 중반~후반 문제 수준
- **10:** Codeforces Div.1 후반 문제처럼 FFT, 금광 세그먼트 트리 등의 고급 기법이나 깊은 수학적 지식, 게임 이론, 어려운 애드혹 발상이 필요한 수준

나머지 난이도는 이 기준점 사이에 체감에 따라 배치하고, 각 문제에 난이도를 부여한 이유를 짧게 기록한다. 특정 알고리즘의 사용 여부만으로 난이도를 결정하지 않는다.

# 제출 규칙

- 최초 생성 코드를 로직 수정 없이 제출하고, 코드 울타리 제거 등 형식 정리만 허용한다.
- 네 모델(`qwen36`, `gemma4`, `luna`, `motif3`)에 같은 10문항을 각 두 회차씩 요청한다. 전체 계획은 모델당 20회, 네 모델 합계 80회다. `--round 1/2`는 반복 번호이며 이전 답변이나 채점 결과를 전달하지 않는 독립 요청이다. 로컬과 Cloud는 제공자·생성 설정이 다르므로 문제 목록·반복 수·독립성만 공통 조건으로 삼는다.
- 유효 정답은 원본 후보가 `AC`이고 적용한 평가 시간 제한 미만으로 모든 테스트를 통과한 경우다. 코드 수정본의 통과는 원본 유효 정답에 합치지 않는다.
- 모델별 정답률의 분모는 항상 20회다. `CALL_ERROR`, `NO_CODE`, `WA`, `RE`, `TLE` 등 유효 정답이 아닌 시도도 분모에서 빼지 않는다. 호출 성공 수·실제 시도 수·미실행 수는 별도로 기록한다.
- 로컬 후보의 최소 품질 통과선은 원본 후보 유효 정답 12/20회(60%) 이상이다. Cloud 모델은 각각 20회 분모를 유지하지만 이 로컬 통과선과 최종 로컬 순위에 합치지 않는다.
- 응답 시간은 품질 통과 조건으로 제한하지 않는다. 모델 호출 실패 시간은 성공 호출 평균과 분리한다.

## 평가 범위와 기준 확정 시점

현재 평가 기준은 생성이 시작된 뒤 확정됐다. 따라서 `configs/evaluation.json`의 `decision_phase`는 `during_generation`, `preregistered`는 `false`로 기록하며 사전등록된 기준이라고 표현하지 않는다. 생성 프롬프트에 제공한 공식 시간·메모리 제한은 바꾸지 않는다. 아래의 유효 제한은 생성과 기준 채점이 끝난 뒤 오프라인 평가 단계에서만 적용한다.

전체 10문항 중 네 문항은 `scoring`으로 전체 테스트를 재평가할 수 있다. 적용 제한은 다음과 같다.

| 문제 ID | 문제문에 제공한 공식 제한 | 평가 단계 유효 제한 |
| --- | ---: | ---: |
| `coci_2025_2026_c5_tezina` | 2초 | 4초 |
| `coci_2025_2026_c5_pet` | 1초 | 2초 |
| `coci_2025_2026_c6_ucionica` | 1.5초 | 3초 |
| `coci_2025_2026_c6_skijanje` | 1초 | 2초 |

나머지 여섯 문항도 공식 1배 제한의 원본 평가와 최소 수정 보조 평가에 포함한다. 기준 세션의 개별 테스트에 `TLE`가 있어 실행하는 2배 제한 재평가만 `diagnostic`으로 둔다. 열 문항의 원본 후보는 모델별 20회 분모에 포함하며, 네 scoring 문항의 2배 결과만 프로젝트 scoring에 반영한다.

기준 세션은 기존 `judge batch`의 공식 1배 시간 제한 판정이다. 열 문항 중 기준 세션의 개별 테스트에 `TLE`가 있을 때만 해당 문항의 전체 테스트를 2배 시간 제한으로 다시 실행한다. 기준 세션에서 이미 `AC`인 항목은 `baseline_1x`로 재사용하고 2배 측정이라고 표시하지 않는다. 네 scoring 문항의 2배 결과는 프로젝트 scoring에 반영하고, 여섯 문항의 2배 결과는 diagnostic으로만 남긴다. 여섯 문항의 1배 원본 판정과 보조 수정 결과는 계속 평가에 사용한다.

## 선정 순서

필수 조건을 충족한 후보 사이에서 다음을 순서대로 비교한다. 앞선 기준이 동률일 때만 다음 기준을 적용한다.

1. 원본 유효 정답률: 높을수록 우선한다.
2. 최소 수정 후 전체 테스트 통과 건수: 많을수록 우선한다.
3. 설명 정확성 평균: 높을수록 우선한다.
4. 전체 모델 응답 시간 평균: 짧을수록 우선한다.

모든 기준이 같으면 동률로 남긴다. 비교에 필요한 기록이나 검토가 미완료면 순위를 확정하지 않는다. 두 후보 모두 60% 미만이면 최소 품질 미충족을 밝히고 상대적 우위와 실제 사용 적합성을 구분한다.

## 최소 수정 보조 평가

보조 수정은 같은 문제의 원본 후보를 대상으로 한다. 인덱스 ±1, 경계 조건, 초기값처럼 원래 알고리즘을 유지하는 제한 수정만 허용하며, 핵심 알고리즘 교체는 허용하지 않는다. 수정본은 원본 후보 파일을 덮어쓰지 않고 저장소 루트 기준 상대 경로의 사용자 수정 파일로 연결한다.

각 원본 후보에는 보조 수정 통과를 최대 한 번만 기록한다. 같은 완료 시도는 중복 실행하지 않으며, 다른 수정 시도는 새 append-only 기록으로 남긴다. 후보로 판단할 때 수정 이유와 `algorithm_preserved=true` 여부를 함께 입력하고, 스냅샷·diff·hash·전체 테스트 판정을 저장한다. 호출 실패와 코드 미생성은 수정 통과로 인정하지 않는다.

수정본이 통과해도 원본 판정·유효 정답률·60% 통과 여부에는 반영하지 않는다. 보조 통과 수는 원본 정답률과 분리된 두 번째 선정 기준으로만 사용하며, 보조 평가가 끝나지 않은 모델의 순위를 확정하지 않는다.

## 설명 정확성

접근법·정당성·시간/공간 복잡도를 원본 응답에서 확인한다.

| 등급 | 점수 | 판정 기준 |
| --- | --- | --- |
| 정확함 | 2 | 접근법·정당성·시간/공간 복잡도가 정확하고 서로 일치한다. |
| 일부 오류 | 1 | 핵심 풀이의 타당성을 무너뜨리지 않는 일부 오류나 누락이 있다. |
| 핵심 오류 또는 설명 없음 | 0 | 핵심 접근·정당성이 틀리거나 설명이 없다. |

실제 응답 부분에 점수 근거를 연결하고 평균·평가 건수 n·등급별 건수를 기록한다. 설명 점수는 사람이 `review.json`에 직접 입력한다. 정상 수신한 낮은 품질 응답과 `NO_CODE` 응답도 설명을 평가한다. `CALL_ERROR`는 설명 점수에서 제외하고 실패 수·실패 시간 n을 별도로 기록한다. 점수가 없거나 아직 검토하지 않은 항목은 0점이 아니라 `missing`·`unchecked`로 남긴다.

성공 호출의 `response_elapsed_seconds`는 코드 유무와 무관하게 평균을 내고 성공 건수 n을 표시한다. 호출 실패로 얻은 경과 시간은 성공 평균에 섞지 않고 별도 실패 시간과 n으로 집계한다.

## 발제 집계와 종료 시점 확인

원본 유효 정답률과 별개로 호출 성공 수/전체 시도 수, 지표별 평균과 n, 대표 성공·실패 사례를 유지한다. 미측정 값을 0으로 채우지 않는다.

질문별 기대 결과와 사례 구분은 [평가 질문 10개](evaluation-questions.md)에 정리했다. 정상·경계 사례는 문항에 대응시켰고, 정보 부족·범위 밖 사례는 공식 테스트 데이터로 채점하는 이 태스크에 대응되지 않아 두지 않았으며 그 사유를 같은 문서에 남겼다. 현재 계획은 로컬 40회와 Cloud 모델별 20회씩을 합한 전체 80회다. 제한 미제공 조건의 과거 10회만 pilot으로 분리하며, 이전 60회 계획에서 생성된 현재 경로의 원본은 현재 80회에 포함한다. **계획한 80회는 2026-09-17에 모두 생성했다.** 호출 성공 78건, Motif-3 `skijanje` 두 회차만 제공자 5xx로 실패했고 분모 20에 남겼다. 채점 78건, 설명 리뷰 80건, 평가 보고서까지 완료했으며 집계는 [평가 보고서](../../results/evaluation/20260917_131133_521417Z_98657c40/reports/20260917_134421_178261Z_7affc20f/report.md)를 따른다. 생성 도중의 35건 일시정지 기록은 [결정 이력](../history/decision-log.md)에 당시 시점으로 보존했다. 현재 서버 Context는 65536, 로컬 본 실험 요청 출력은 61440·reasoning 53248·temperature 0·cache_prompt false로 맞췄다. [기존 reasoning 종료 메시지](../history/reasoning-budget-diagnostic.md)는 유지한다. 이전 설정의 관측과 구분하며 새 결과에는 해당 메시지도 저장한다. 워밍업은 호출만 하고 기록하지 않기로 했다. environment 인자와 자동 환경 기록·검증은 제거하고 본 실험의 성능·실패 기록은 유지한다. 실행별 실제 적용 설정·VRAM 관측은 각 `result.json`에 남겼고, 워밍업은 무저장 방침이라 파일 증빙이 없다. 관측 범위와 미확인 항목은 [실행 환경](../operations/environment.md)을 따른다. 이미 일부 로컬 결과를 본 뒤 전체 세트 적용을 결정했으며 이를 사전 확정으로 소급하지 않는다.

## Cloud 비교 확장 기준

과정의 기본 Cloud 비교 범위였던 모델 1개·공통 5문항×1회와 이번 수행을 [과제 요약](assignment.md)에 구분했다. 사용자 수행 기준은 Luna·Motif-3 각각 기존 10문항 전체를 두 번 독립 실행하는 10문항×2회=20회로 확장한다. 별도의 5문항 실행·집계 분모는 만들지 않는다.

Cloud 비교 대상은 **Luna와 Motif-3 두 제공자**로 확장한다. 이는 발제 원문의 Cloud 1개 기준을 넘는 추가 사용자 확장이며, 원문 기준을 충족한 뒤 덧붙이는 비교다. 두 모델은 같은 10문항·같은 프롬프트·같은 Judge를 쓰지만 제공자·API 계열·생성 설정이 서로 다르므로 각각 20회의 독립 분모를 유지하고 하나의 Cloud 분모로 합치지 않는다. 한 모델만 실행한 시점에 Cloud 비교가 끝났다고 표시하지 않으며, 미실행 모델은 실패가 아니라 미실행으로 구분한다. 일부 로컬 결과를 본 뒤 전체 세트 적용을 결정했으며 사전 5문항 선정으로 소급하지 않는다. 현재 전체 계획은 로컬 40회와 Cloud 40회를 합친 80회다.

[Cloud 실행 조건](../operations/cloud-runbook.md)은 Luna가 Responses API·reasoning=max·max_output_tokens 128000이고, Motif-3는 Chat Completions 호환 API에 모델과 단일 user prompt만 보내며 나머지는 제공자 기본값이다. 로컬과 Cloud는 같은 10문항을 두 회차씩 독립 실행하지만 제공자·생성 설정은 다르다. 문제 목록·반복 수·독립성만 공통 비교 축으로 삼고, 토큰 예산·temperature·reasoning 설정을 동일 조건으로 표시하지 않는다. 이는 Luna와 Motif-3 사이에도 똑같이 적용한다. 로컬 모델당 20회와 Cloud 모델당 20회를 구분하고 실패·NO_CODE도 각 분모에 포함하며 미실행은 별도로 표시한다. 로컬과 Cloud 모두 두 회차 중 좋은 결과만 선택하지 않는다. 로컬 60% 통과선과 최종 로컬 선정 순위에 Cloud를 합치지 않으며 Cloud는 최종 로컬 후보 선정에서 제외한다.

응답·상태·네트워크 포함 시간·토큰·예상 비용을 기록하고, 실제 사용 내역·지표별 n·품질 근거와 구분한다. 예상 비용은 공개 단가표를 확인한 모델에만 기록한다. Motif-3는 확인한 단가표가 없어 사유와 함께 null로 남기며, 비용 축에서는 Luna와 나란히 비교하지 않는다. 보안·인프라·운영·커스터마이징 비교와 집계·설명 채점은 후속 작업이다. 실제 결과 내용과 완료 범위를 확인하기 전에는 Cloud 비교 완료로 표시하지 않는다.

## 실행 제한과 결과 경로

- 로컬·Cloud에 동일한 문제문과 공식 시간·메모리 제한을 제공한다. 제한값은 `data/coci/problems.json`에서 읽어 문제 바로 위에 명시하며 다른 메타데이터는 전달하지 않는다.
- Judge는 테스트별 시간 제한과 stdout·stderr 합산 출력 10 MiB(10,485,760 bytes)를 적용한다. TLE와 OLE가 함께 발생하면 먼저 발생한 자원의 판정을 남기며, 인프라·처리 예외는 `JUDGE_ERROR`로 기록한다. `judge_policy` 메타데이터에 per-test byte limit, combined stream scope, first-trigger precedence를 남긴다. 코드 메모리 사용량·RSS 측정, 메모리 제한 강제, MLE 판정은 구현하지 않으며 AC는 메모리 제한 준수를 증명하지 않는다.
- 결과 경로는 `results/benchmark/<문제>/<모델>/round_<회차>/`다. 모델 폴더는 `qwen36`·`gemma4`·`luna`·`motif3`이며 로컬 2회·Cloud 모델별 2회 구분과 각 분모를 유지한다.
- 제한 미제공 프롬프트의 과거 로컬 6회·Cloud 10회는 pilot으로 분리하고 현재 80회에 합산하지 않는다. 이전 60회 계획에서 생성된 현재 경로의 원본은 현재 80회에 포함하며 pilot으로 옮기지 않는다. 원본을 다시 쓰거나 이전 답변을 새 모델 입력에 넣지 않는다.

기준 세션 생성과 제한 재평가·보조 수정·설명 입력·보고서 생성 절차는 [평가 실행 안내](../operations/evaluation.md)를 따른다. `judge candidate`로 별도로 확인한 결과는 평가 보고서에 자동 편입하지 않는다.
