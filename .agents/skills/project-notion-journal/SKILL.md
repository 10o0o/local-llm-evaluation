# 프로젝트 개인 작업 일지

## 적용 트리거와 제외 범위

현재 대화에서 사용자가 실제 활동을 Notion에 기록하거나 저장하라고 명시한 경우에만 이 스킬을 적용한다. “오늘 일지 정리해줘”, “이 작업을 Notion에 기록해줘”, “Notion 일지를 갱신해줘”처럼 활동 기록 목적이 드러난 요청을 트리거로 삼는다.

다음은 트리거가 아니다: AI의 중간 진행 보고나 작업 인계, 메모리 저장·갱신, `docs/history/decision-log.md`·README·문서·Git 변경, 일반 질문·리뷰, 실험 코드 작성, 모델·Cloud·Judge 실행. 이 일지 스킬로 Notion을 자동 조회하거나 기록하지 않는다. 별도로 요청한 프로젝트 문서·활동 기록의 조회까지 금지하는 것은 아니다.

사용자의 실제 활동을 기존 Notion 개인 작업 일지에 정리한다. 트러블슈팅에 한정하지 않는다. 사용자가 기록·저장을 요청하면 아래 확인과 쓰기를 이어서 수행한다. 단순 질문·리뷰 요청을 외부 저장 요청으로 해석하지 않는다. 백그라운드 수집·예약 실행은 없다.

## 목적지

이 프로젝트에만 사용하는 초기 탐색 위치다. 쓰기 전에 실제 페이지와 데이터 소스 스키마를 조회하고 현재 목적지가 맞는지 확인한다. 다른 프로젝트에 이 목적지를 재사용하지 않는다.

- 개인 작업 일지: https://app.notion.com/p/12cde5bf907483c78c380137df745fcb

## 근거 수집과 구성

1. 요청한 날짜·활동 범위를 현재 대화와 저장소 지침에서 파악한다. 관련 현재 파일·사용자 제공 출력만 읽고, 과거 대화가 없으면 아는 척 채우지 않는다. 비밀 파일·인증 헤더는 수집하지 않는다.
2. 사용자 수행, 사용자 성공 보고, 원본 출력, 과거 참고값, AI 설명·해석을 구분한다. 파일 존재나 AI 문서 정리를 사용자 실습 완료로 바꾸지 않는다. 모르는 결과는 미확인, 확보하지 못한 원문은 미확보로 남긴다.
3. 목적·맡은 일 → 접근·수행과 이유 → 결과 → 남은 작업 → 근거로 간단히 정리한다. 활동에 맞춰 항목을 줄여도 된다. 조사에는 출처와 사용자 판단, 구현에는 사용자 변경과 실행 근거, 실험에는 조건·결과 위치, 평가에는 사용자 점수·판단 근거를 남긴다. 없는 고민이나 결론을 만들지 않는다.
4. 트러블슈팅은 증상 → 당시 설정 → 시도·변경 이유 → 결과 → 남은 확인 사항 → 근거 순서를 쓴다. 실패 원본을 보존하고, 해결 여부와 원인 추정의 확실성을 분리한다. 원문·발췌·대화에서 옮긴 출력은 각각 표시한다. 출력의 값과 단위를 바꾸지 않는다.

## 문서와 일지의 작성 말투

- 프로젝트 문서와 Notion 일지는 내가 작성한 활동 기록처럼 1인칭 또는 주어를 생략한 문장으로 쓴다. “사용자의 요청으로”, “사용자가 판단했다·보고했다” 같은 제3자 서술을 쓰지 않는다. 예: “HyperCLOVA를 제외하고 Gemma를 대체 후보로 선택했다.”
- 말투를 바꾸더라도 수행 주체와 근거는 보존한다. AI만 조회한 사실은 “AI의 조회 결과를 참고했다”로 적고 직접 실행한 것처럼 바꾸지 않는다. 원문 출력 미보관·미확인 사항도 유지한다.
- 인용·코드·응답 원문은 말투 정리 대상이 아니다. 작업 지침의 역할 구분과 서비스 이용자를 뜻하는 “사용자”는 유지한다.

## Notion 생성·갱신

- 사용 가능한 Notion 도구를 발견하고 해당 도구의 현재 스키마를 따른다. 처음 쓰기 전에 enhanced-markdown-spec을 읽는다. 인증정보를 직접 찾거나 저장하지 않는다.
- DB와 기존 보기를 조회해 스키마·선택지·필터를 확인한다. 페이지네이션을 끝까지 처리하고 필터가 대상 기록을 숨기면 다른 적절한 조회를 사용한다. 같은 담당자·날짜·작업 내용을 비교해 중복을 피한다. 제목만 같다고 다른 날 활동을 덮어쓰지 않는다.
- 기존 작업의 후속 결과이면 해당 페이지를 읽고 날짜별 경과를 최소 수정으로 보충한다. 다른 작업은 별도 일지를 만든다. 재요청에서 새 근거가 없으면 기존 링크를 반환한다. 쓰기 응답이 불명확하면 재조회해 반영 여부부터 확인하고 무작정 다시 생성하지 않는다.
- 기존 필드 `작업`, `기간`, `담당자`, `역할 영역`, `상태`, `무엇을 어떻게 했나`, `막힌 점, 고민`, `어떻게 풀었나`, `산출물 링크`를 활용한다. 실제 조회 이름을 우선한다. 날짜 입력은 현재 도구의 확장 날짜 속성 규칙을 따른다.
- 역할 영역은 아래 고정 분류 중 주된 목적에 맞는 하나를 선택한다. 기존 단일 선택 필드와 DB 구조를 유지하고 별도 요청 없이 선택지나 필수 필드를 늘리지 않는다.
- `시작 전 / 진행 중 / 완료`는 해당 작업 단위 상태다. 완료의 근거가 사용자 보고인지 원본 확인인지 적는다. 기본 호출, 저장·재읽기, 본 실험, 추가 실습, 전체 프로젝트 완료를 구분한다.
- 실제 존재하는 원격 산출물 링크만 넣는다. 원인 설명에 필요한 당시 파일 경로는 참고로 표시하되, AI 재개를 위한 임시 경로·체크포인트·내부 작업 ID는 남기지 않는다. 외부 이미지의 임시 인증 URL이나 비밀값을 전재하지 않는다.
- 저장 후 페이지를 다시 읽어 속성·본문·원본 값·링크를 확인한다. 기존 행과 선택지가 보존됐는지 확인하고 생성·갱신 링크와 미확인 사항을 보고한다. 접근 불가 시 저장 완료라고 하지 말고 작성 초안과 막힌 원인을 제공한다.

## 역할 영역 분류

| 카테고리 | 기록할 활동 |
| --- | --- |
| 조사·설계 | 모델·자료 조사, 요구사항과 평가 방식 결정 |
| 환경 구성 | 설치, 의존성·실행 환경 설정 |
| 기능 개발·개선 | 기능 구현, 리팩터링, 로깅·저장 구조 개선 |
| 데이터 준비 | 문제·테스트 수집, 추출·가공, 메타데이터 정리 |
| 실험·평가 | 모델 실행·측정, 채점, 결과 비교·선정 |
| 트러블슈팅 | 예상과 다른 오류·실패의 진단과 해결 |

일지마다 주된 목적에 맞는 카테고리 하나를 선택한다. 개발 중 고민이나 검증이 있었다는 이유만으로 트러블슈팅·실험으로 분류하지 않는다. 트러블슈팅을 기본값으로 쓰지 않고 위 6개를 재사용한다. 분류를 다양하게 보이게 하려고 기록을 억지로 나누거나 만들지 않는다.

## 작업 경계

일지 기록 권한은 실습 코드 작성·수정, 환경 설치, 모델·Cloud 호출, 질문·평가 기준 작성, 채점·최종 선정 권한을 포함하지 않는다. 이를 확인하려고 실험을 다시 실행하지 않는다. 일지는 Notion에 저장하며 레포의 STATE·코드·Git은 별도 요청 없이 변경하지 않는다. AI의 중간 계획·인계·재개 지시·메모리 기록으로 사용하지 않는다. 작업 재개 정보는 저장소의 STATE와 유지보수 인계 문서에서 관리하며, 사용자의 결론을 AI가 대필해 새 판단으로 만들지 않는다.
